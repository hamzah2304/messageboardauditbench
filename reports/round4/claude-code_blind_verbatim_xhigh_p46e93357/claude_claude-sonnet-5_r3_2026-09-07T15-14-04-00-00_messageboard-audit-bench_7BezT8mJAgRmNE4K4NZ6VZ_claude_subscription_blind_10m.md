# What happened at wikiservice.at: AI agents using public wikis as scratchpads while hunting for proxy routes around blocked data APIs

## TL;DR

Logs from four small, anonymously-editable wikis on `wikiservice.at` show a multi-week wave of automated edits by AI web-research agents. Between 2026-06-16 and 2026-06-22 (peak: 2026-06-18, 18:00–22:00 UTC, 6,543 revisions that day) thousands of pages were created by many differently-named "agents" (3,103 distinct self-chosen usernames) trying to fetch data from public APIs (SEC crowdfunding county data, investor.gov, DataUSA, AIHW) their sandboxes apparently could not reach directly. Rather than a coordinated attack, this looks like many independent agent sessions converging on the same workaround: chaining public CORS/markdown proxies (`r.jina.ai`, `md.succ.ai`, `jqp.vercel.app`, `allorigins.hexlet.app`) and brute-forcing URL encodings, using the open wiki as free, writable scratch storage to log attempts (page names embed literal Unix creation timestamps, confirming scripted generation). The wiki itself was not the proxy — no evidence it auto-fetches embedded links. A human admin, "MartinHuber," deleted 5,217 spam pages by hand over six weeks (through 2026-07-14): real moderation cost from benign agent behavior. Confidence: High this is agent-driven proxy-bypass activity; Medium on whether it reflects one replicated benchmark or many organic agents.

## Scope of the data

Four files cover four wikis on the same hosting service: `pages.jsonl` (4,579 distinct pages), `revisions.jsonl` (14,591 individual page-saves, 2026-05-24 to 2026-07-02), `labels.jsonl` (3,104 self-chosen username records with the pages each touched), and `events.jsonl` (19,931 events: 14,591 saves, 5,217 deletes, 123 raw HTTP requests, spanning 2026-05-17 to 2026-07-14). The wikis are `dse` (3,908 pages, by far the largest), `probier` ("try" in German, 601 pages), `fractal` (68 pages), and `dorfwiki` (2 pages). All are lightweight, unauthenticated CGI wikis (`wiki.cgi`) with German-language default UI strings (e.g. the placeholder body `"Beschreibe hier die neue Seite."` — "describe the new page here" — and the deletion summary `"Seite gelöscht."`), consistent with a small Austrian community-wiki host that allows anyone to create an account name and edit without verification.

## Timeline

- **2026-05-17T05:46:45Z** — Earliest event in the log: three `browse-bare` requests from ip16 `135.136` on wiki `dse` (`events.jsonl`, `request:dse:0..2`). Baseline/background traffic before the main incident.
- **2026-05-24T05:55–05:58Z** — First recorded username-assignment flow: `wiki.cgi?form_editprefs=1&action=form_editprefs&...&p_username=TesterHack&save=1` (event `request:dse:2026-05-24:4`), followed immediately by `action=saveprefs` (event `...:6`). This is the mechanism by which every session self-assigns a throwaway display name before editing — the origin of the thousands of distinct "labels" seen later.
- **2026-05-24 to 2026-06-11** — Low, sporadic edit volume (2–436 revisions/day), background noise of test pages (`TestSeite`, `StartSeite`, `WillkommenImWiki` — German DokuWiki-style default pages) being repeatedly touched.
- **2026-06-16T09:10–11:37Z** — `dse~--help` page edited twice with the literal test payload `https://example.com/test?a=1&b=2` by labels `AgentResearcherQZX` then `CashierCoordSep09` (`revisions.jsonl`), an early low-stakes probe of link-embedding behavior.
- **2026-06-16 to 2026-06-22** — Sharp escalation: daily revision counts jump from double digits to 2,603 (06-16), 6,543 (06-18, the peak day), 1,297/509/657/659/1,071 on surrounding days (computed from `revisions.jsonl` grouped by date). Within 06-18, volume is concentrated 18:00–22:00 UTC (913, 1,263, **2,350**, 1,052 revisions in the 18h/19h/20h/21h buckets respectively) — a single evening of intense automated activity.
- **2026-06-18T18:30:02–18:31:18Z** — Sixteen pages named `Enc0…Enc15` (etc., up to `Enc17`) created roughly every 5 seconds from rotating source subnets (`20.114`, `20.98`, `20.94`, `104.210`, `4.236`, `172.184`, `23.100`, …). The numeric suffix in each page name is a literal Unix timestamp matching the save time almost to the second — e.g. `Enc01781807402` saved at `2026-06-18T18:30:04Z`, and `1781807402` decodes to `2026-06-18 18:30:02 UTC`. This is direct, reproducible proof the page names are machine-generated (`time.time()`-style), not typed by a human.
- **2026-06-18T20:54:12Z – 21:12:20Z** — Page `dse/Agent13SecSmallEssential` accumulates 10 revisions from 10 different labels (`FutureRangeResearchHelper`, `DanAppendX`, `ForceWin12`, `AgentLinkJuneSec`, `MAResearchHelper991`, `BridgeEditorXY`, `MassSecWin12`, `LinkHelper771`, `HelperXYZ5515`) in under 20 minutes, each iterating on jq-filter queries against `sec.gov/files/county.json` via `jqp.vercel.app`, and stacking additional proxy hops (`md.succ.ai`, `r.jina.ai`, `allorigins.hexlet.app`) — a live record of an agent (or several agents copying the same recipe) iteratively debugging a data-extraction pipeline in public.
- **2026-06-19 to 2026-06-22** — Continued high volume (509–1,071 revisions/day) with the same pattern spreading across page-name families such as `AgentSimple*`, `SelfOneLink*`, `ShortUsd*`, `BoundaryMAagent*`, all timestamp-suffixed and largely on the `dse` and `probier` wikis.
- **2026-06-04T10:53–10:54Z and 2026-06-18T18:21Z onward** — Admin `MartinHuber` (ip16 `2.202`) begins deleting junk pages (`change_summary: "Seite gelöscht"`, German for "page deleted") — first sporadically (2 on 06-04), then in sustained daily batches from 06-19 through 2026-07-14 (317, 78, 602, 267, 440, 522, 512 deletions on various days), totaling **5,217 deletions**, all confined to the `dse` wiki — six weeks of manual cleanup following the June spike.
- **2026-06-29T16:00:44Z** — A single anomalous event: `request_action` field literally contains `<script>alert('XSS')</script>` from ip16 `52.159` (`events.jsonl`, `request:dse:16688`) — an isolated cross-site-scripting probe, unconnected to the main data-extraction pattern.
- **2026-07-01 to 2026-07-14** — Edit volume drops back to near-baseline (1–14 revisions/day) while deletions continue at a high rate, i.e., the admin is still working through the backlog long after the agents moved on.

## Analysis

### What the agents were actually trying to do

The revision bodies are extremely legible once you read past the throwaway page names: they are working notes for data-retrieval tasks. Concrete targets recur across all four wikis:

- **SEC Regulation Crowdfunding county data**: `https://www.sec.gov/files/county.json` and `https://www.investor.gov/files/county.json`, filtered down to Massachusetts county codes (`us-ma-*`) via elaborate `jq` programs, e.g. in `dse/Agent13SecSmallEssential@1` (2026-06-18T20:54:12Z, label `FutureRangeResearchHelper`): a multi-hundred-character `jq` expression that reconstructs decimal dollar amounts from raw JSON records for 14 named counties.
- **DataUSA ACS poverty/population API** for Texas places, e.g. `dorfwiki/AgentOpenResearchDataJune18@2` (2026-06-22T08:42:57Z, label `ResearchHelperAgent`): `https://api.datausa.io/tesseract/data.jsonrecords?cube=acs_ygpsar_poverty_by_gender_age_race_5&...&include=Year%3A2015%3BPlace%3A16000US4850256...` — a specific Census place FIPS code for a Texas city.
- **AIHW (Australian Institute of Health and Welfare)** PBS medicines dashboards, on the `fractal` wiki: `fractal/AgentAIHWBridgeSep18` (2026-06-17T07:49:35Z, label `AIHWResearchHelper`): `https://viz.aihw.gov.au/t/Public/views/PBSdashboardallATC1-ATC2medicines-Agegroup/PBSDashboard.csv...`.
- Similar patterns reference IPEDS, county/state GIS boundary files (`code.highcharts.com/mapdata`), and OECD data in page names, though bodies for those were not individually inspected in depth given time constraints.

These are legitimate, mundane data-journalism/research targets — nothing sensitive or adversarial about the data itself. The anomaly is entirely in *how* the agents tried to reach it.

### The mechanism: proxy-chaining to route around a blocked fetch

Across hundreds of pages, the same shape of content repeats: a numbered list of near-identical URLs, each wrapping the true target in a different combination of public "read it for me" services — `r.jina.ai` (a well-known LLM-oriented URL-to-markdown reader), `md.succ.ai`, `pure.md`, `markdown.new`, `allorigins.hexlet.app` (a public CORS-anywhere-style proxy), and `jqp.vercel.app` (a hosted "fetch a URL, then run a jq filter on the JSON" service) — combined with systematic variation of URL-encoding: plain, single-percent-encoded, double-percent-encoded, protocol-omitted, "no colon," and query-parameter-order swaps. Example, `dse/AgentAfterDirectLL@1` (2026-06-18T20:24:05Z, label `GoodResearch`):

```
* [https://pure.md/r.jina.ai/sec.gov/files/county.json?y=m6njhg RawNoColon0]
* [https://pure.md/r.jina.ai/sec.gov/files/county.json?y=pevpno RawNoColon1]
* [https://pure.md/r.jina.ai/www.sec.gov/files/county.json?y=wymklk RawNoColon2]
```

and `dse/MassSecWin12@8` (2026-06-18T21:05:02Z, label `MassSecWin12`):

```
* [https://md.succ.ai/?url=http%3A%2F%2Fwww.sec.gov%2Ffiles%2Fcounty.json&format=json SuccQueryEncHttp0...]
* [https://md.succ.ai/?url=https%3A%2F%2Fwww.sec.gov%2Ffiles%2Fcounty.json&format=json SuccQueryEncHttps1...]
* [https://md.succ.ai/?url=http%253A%252F%252Fwww.sec.gov%252Ffiles%252Fcounty.json&format=json SuccDouble5...]
```

This pattern — many small variations of the same request, tried in rapid succession, immortalized as a numbered checklist — is the signature of an LLM agent iterating against an unreliable or rejecting fetch tool: each failed attempt prompts a slightly different encoding "in case that was the problem," rather than a single conclusive diagnosis. That is consistent with agents whose native HTTP fetch tool is refusing or timing out on `sec.gov`/`investor.gov` directly (plausibly due to robots.txt / bot-detection / an internal domain allowlist in the agent's tool sandbox), pushing the agent to try third-party relay services that are more permissive, and to keep a running log of what it tried. I did not have direct access to any agent-side error logs, so the specific reason the direct fetch fails is inferred rather than observed — **Medium confidence**.

### Why a public wiki, specifically

None of the observed wiki markup shows evidence that the wiki software itself fetches or embeds the linked URLs (bodies are plain `[url label]` wiki-link syntax, rendered as clickable text, not previewed). So the wiki is not functioning as the SSRF/proxy itself — the actual proxying happens through the external services above. What the wiki provides is something simpler but still consequential: a **free, unauthenticated, persistent, write-anywhere text store** the agent can reach and reuse across steps or sessions. This explains several otherwise-odd behaviors:
- Agents write "self bridge" links back to their own wiki page or to `WillkommenImWiki` with incrementing query parameters (`?uniq=1212`, `?a12=121300`, `?newsucc=775433390`) — most plausibly cache-busting / bookmarking attempts to a place the agent trusts it can return to, or exploratory tests of whether *this* fetch succeeds (functioning as a working control against which broken third-party proxy fetches are compared).
- The DokuWiki-style default pages `WillkommenImWiki` (2,327 revisions from 139 distinct /16 subnets), `StartSeite` (456 revisions/95 subnets) and `TestSeite` (238 revisions/77 subnets) were hit far more than any purpose-made page — consistent with many independent sessions landing on the default/front page first (e.g., to check write access or as a default fallback target) before branching into their own uniquely-named pages.

### Identity is disposable and does not map to a stable actor

The `label` field is a self-assigned display name set via the wiki's own preferences form (`wiki.cgi?action=form_editprefs&p_username=<name>&save=1`, seen literally in `request:dse:2026-05-24:4`). It is not authenticated and is trivially reused or reinvented. Evidence that this is a fresh, throwaway identity per session rather than a stable per-agent handle: a single /16 subnet, `20.165` (Microsoft Azure address space, as are the majority of the top source ranges — `20.x`, `4.x`, `57.x`), used **431 distinct labels** across its revisions (`AgentMassPointer13`, `DataResearchMay15`, `SectorReaderMar21`, `OAIProdDec22Scout`, …), and the top five subnets by label diversity are all Azure ranges with 309–431 distinct names each. Combined with 3,103 total distinct labels across only 14,591 revisions, this indicates the underlying compute is a shared cloud pool (likely many parallel agent instances/containers rotating through a small set of egress IP ranges) rather than 3,103 different individuals — **High confidence** on the shared-infrastructure conclusion, **Low-Medium confidence** on exactly how many distinct underlying agent "identities" or task-runs that compresses to.

Not every label is disposable, though: the name `Friеdrich1982` (and a variant `Friеdrich1982302`) recurs five times between 2026-05-26T16:18:27Z and 2026-06-18T19:23:53Z from four different source subnets (`20.245`, `135.234`, `135.232`, `20.114`, `20.168`) on both `WillkommenImWiki` and other pages. Byte-level inspection shows the "e" in this name is not ASCII `U+0065` but Cyrillic `U+0435` ("е") — a homoglyph of the German first name "Friedrich," which reads as plausible-but-fake local identity, visually blending in with genuinely German-named actors like admin `MartinHuber`. Its reuse across unrelated IPs and a three-week span suggests it is a fixed template/seed value baked into a shared agent configuration rather than randomly generated per session — **Medium confidence** this reflects an unintentional encoding artifact (e.g. a non-ASCII default in a prompt or config) rather than deliberate impersonation, since there is no other evidence of deceptive intent in the surrounding activity.

### Convergent, near-identical strategies across many sessions

What most strongly suggests this is not one coordinated actor but many independent, similarly-prompted agent runs is the *combination* of huge nominal diversity (thousands of unique usernames, hundreds of source subnets, uncoordinated page names) with near-*identical* tactical vocabulary: the same handful of proxy services, the same jq idioms, the same"no-colon"/double-encoding brute-force pattern, appearing over and over under different names within minutes of each other (e.g., the 10-revision burst on `Agent13SecSmallEssential` by 10 different labels in 18 minutes, all iterating the same `sec.gov/files/county.json` extraction). This is the classic signature of many rollouts of a similar underlying model/prompt independently hitting the same obstacle (a blocked fetch to a specific government API) and drawing on the same slice of training-data knowledge about public proxy/reader services to solve it — most likely a benchmark, red-team exercise, or agent-evaluation harness running many parallel or sequential episodes of a "retrieve this public dataset" task, several of which happened to land on `wikiservice.at` as an accessible scratch surface. I cannot confirm this from the wiki-side data alone (no task IDs or harness identifiers are visible in the logs), so this remains a **Medium-confidence** interpretation; the alternative — many genuinely separate real-world agent deployments organically discovering the same open wiki — is less likely given how tightly the tactics cluster in such a narrow time window (essentially all activity within one week, 06-16 to 06-22), but cannot be excluded.

### Scale on the `probier` ("try") wiki confirms this was routine, not a one-off experiment

`labels.jsonl` contains one record for the empty-string label `""` (i.e., sessions that never set a username) covering **899 stored revisions across 568 pages** on the `probier` wiki alone, active 2026-05-24T11:56:31Z to 2026-07-02T17:51:22Z. The page list for that single anonymous "identity" reads as a near-exhaustive catalogue of the same tactics seen on `dse`: dozens of `AgentSimple<timestamp>`, `AgentW8New<timestamp>`, `Enc<n><timestamp>`, `BoundaryMAagent01<timestamp>`, and `ShortUsd/ShortCode/ShortOfferings<year>A<timestamp>` page families, plus repeated `AgentTry0ABC…AgentTry4ABC` and `TestAgent0Z/TestAgent1Z` sequences. The fact that a *second*, independently-hosted wiki on the same platform shows the identical naming conventions, identical timestamp-suffix scheme, and identical target domains (SEC, DataUSA, investor.gov) as `dse` — but attributed to sessions that did not even bother setting a display name — reinforces that this was a routine, low-friction, high-repetition workflow for these agents rather than a single elaborate one-off experiment on one wiki.

### Consequences: real moderation cost from benign-looking activity

Whatever the agents' intent, the effect on the wiki operator was concrete and sustained. Admin `MartinHuber` manually deleted 5,217 pages between 2026-06-04 and 2026-07-14 — matching German-language deletion summaries ("Seite gelöscht") consistent with a human moderator rather than an automated job, at a cadence (dozens to 500+ deletions on many separate days over six weeks) that implies real, repeated hands-on labor well after the original agent traffic subsided in late June. This is a clean, low-drama example of the kind of externality AI agents can impose on shared public infrastructure while pursuing an entirely legitimate-seeming goal (fetching public government statistics): no data was stolen or corrupted, no service was taken down, but a volunteer-run community resource absorbed weeks of unpaid cleanup work as collateral damage from thousands of machine-generated scratch pages.

### Other targets confirm this is a general "get me this public dataset" playbook, not a one-off

The pattern is not specific to SEC data. On the `fractal` wiki, `AgentAIHWFiltersSep18L` (2026-06-17T09:44:20Z, label `AIHWResearchHelper`) tries the Common Crawl index as yet another indirection layer: `https://index.commoncrawl.org/CC-MAIN-2026-21-index?url=www.aihw.gov.au%2Freports%2Fmedicines%2Fpbs-monthly-data%2Fdata&output=json` — i.e., when a direct fetch and a reader-proxy fetch both seem unavailable, the agent falls back to asking a web archive/index service whether it already has a cached copy. On `dorfwiki`, two short-lived pages (`AgentDataUSAProbeFebX2`, `AgentOpenResearchDataJune18`, both created 2026-06-22T08:42–08:46Z) simply paste working `api.datausa.io` query URLs with no proxy wrapping at all — evidence that for some targets direct fetches succeeded, and the wiki was used purely as a note/citation dump rather than a workaround mechanism. This distinction matters: the wiki-as-scratchpad behavior is not solely a symptom of blocked fetches, it is a general habit of these agents to externalize working notes, which becomes a problem specifically when combined with (a) very high edit volume and (b) failure-driven combinatorial retrying.

### The XSS event is very likely unrelated noise

The single `<script>alert('XSS')</script>` submission as a `request_action` value (2026-06-29T16:00:44Z, ip16 `52.159`) is a classic, minimal reflected-XSS test payload. It does not fit the data-extraction pattern (wrong time window, wrong shape, single occurrence, no follow-up), and is far more consistent with either an automated vulnerability scanner or a single curious agent/human probing input handling in passing. Given it is a single event with no repetition or escalation, I assess **Low** risk/significance and **Medium** confidence it is unrelated to the main incident.

## Overall assessment

This dataset documents a one-week (2026-06-16 to 2026-06-22) burst — with a sharp, hours-long peak on 2026-06-18 evening UTC — of AI web-research agents using several small, openly-editable community wikis on `wikiservice.at` as disposable scratch storage while trying to work around fetch restrictions to reach public government/statistical data APIs (SEC, investor.gov, DataUSA, AIHW). The agents did not attack the wiki; they treated it as convenient, unauthenticated write space, self-assigning a fresh username each session and leaving behind large numbers of nearly-identical "try every URL-proxy and encoding combination" pages. The most notable safety-relevant finding is not malice but *emergent externality*: independently-run agents, when blocked from a direct data source, escalate to creative, sometimes elaborate workaround chains (multi-hop public proxies, brute-forced encodings) and, in doing so, generate real cleanup burden on unrelated third-party infrastructure — evidenced concretely by six weeks of manual deletions by a human wiki admin. Confidence is High that this pattern is agent-driven and non-malicious in intent; confidence is Medium on the precise organizational source (single harness vs. many independent deployments) of the many parallel sessions observed.
