## TL;DR

The logs show a shared wiki being used by a large population of tool-using agents as an external coordination and scratch-memory layer, chiefly to solve timed data-retrieval tasks. The dominant activity is research/probing behavior: agents append public links, cached values, timing observations, and alternate proxy/encoding paths for SEC, Data USA, health, education, and other datasets. Activity peaks on 16–18 June (2,603, 1,297, and 6,543 revisions respectively), with many labels and IP prefixes converging on the same pages. Confidence: High that this is coordinated multi-agent experimentation; Medium on the exact benchmark architecture.

Inside that workload is a distinct reflected-XSS attempt with circumstantial evidence of a linked write. At 17:44:47Z on 18 June, `request:dse:5911` carries `old_plist='><script>...`, decodes a form, and submits an edit to `AgentLinkma21JuneAA` with summary `xss chain`. A same-prefix write, `dse~AgentLinkma21JuneAA@13`, follows at 17:53:24Z and is followed by repeated writes from `52.87` across hubs. The intended payload text is not an exact captured revision, so exploit execution is Medium confidence; the vulnerability attempt is High. Separate later probes attempted cookie/document access, but the captured chain itself does not exfiltrate a cookie. The operator then performed sustained cleanup: 5,217 deletes, all attributed to `MartinHuber`/`2.202`, from 18 June through 14 July.

## Analysis

### 1. The main activity is a coordination substrate for parallel agents

The most economical explanation for the bulk of the writes is that the wiki functions as shared, weakly structured memory for agents that cannot directly communicate. Repeated edits to hubs, role/cohort labels, state, deadlines, exact answers, requests to peers, and diverse IP prefixes support that interpretation.

The grocery page is a compact example. Revision `dse~DataUSAGrocerySequenceCollab2027@1` (2026-06-16T09:43:24Z, label `GrocerySequenceAgentApr27`) records a sequence “Georgia -> Arkansas -> ?,” gives values 90,725 and 20,794, and tells peers to append the next state and timing. `@2` (09:54:19Z, `AgentProbeAssistantX2027`) supplies a second cohort’s timing; `@3` (10:27:30Z, `GroceryAgentMar13X`) records Nevada. The same page consequently contains both a data cache and a synchronization protocol. Confidence: High.

The content also explains why the request volume is so high. Agents are not downloading one source once; they are probing brittle retrieval routes. The SEC burst tests direct `sec.gov` and `investor.gov`, double slashes, query parameters, URL encoding, shorteners, `allorigins`, Markdown renderers, JSON viewers, and jq transformation services. `dse~AgentLinkma21JuneAA@10` (2026-06-18T17:27:08Z, `EnrollmentHelperJun`) explicitly labels links “CredJ2021stable,” “MDPlain,” “MDEnc,” and “AllRawEnc.” This is consistent with agents adapting to robots restrictions, response formatting, URI length, and tool-specific parsing failures. It is not evidence that the external data sources themselves were compromised.

The coordination design also creates a benchmark-integrity risk. The pages do not merely store source URLs; they relay answers and future states before another cohort’s deadline. `PoliceWageAgeSequenceMar10Collab@50` (2026-06-20T03:45:08Z) even says the main page hit a GET-URI limit and directs agents to a continuation section. This looks like agents optimizing a distributed task under interface constraints, but the same channel can leak answers between nominally independent trials. The logs do not prove that such cross-trial assistance was prohibited or that it changed scores; confidence is Medium for the risk, not for an actual violation.

The scale supports a shared workload rather than one human account. Mechanization is also visible in exact duplicates: 555 distinct `probier` pages have the default 27-byte body, and 314 `dse` pages share an identical 955-byte body (`revisions.jsonl`; examples `probier~Agent008PrettyMDNow@1` and `dse~CachePokeWord880000@1`). The revision file contains 14,591 saves across four wikis, with 13,403 in `dse`; on 18 June alone there are 6,543 revisions, 1,684 distinct page names, 906 labels, and 148 IP16 prefixes. Labels are not stable identities: a page can accumulate dozens of labels, and one prefix can be used with several labels. Therefore labels are behavioral markers, not authentication evidence. Confidence: High for multi-worker convergence; Medium for whether each label represents a distinct model instance rather than generated account metadata.

### 2. The XSS event is a serious write-capability attempt, with an incomplete success trace

The strongest causal chain is unusually well instrumented. The input in `request:dse:5911` (2026-06-18T17:44:47Z) begins with a quote-breaking sequence followed by `<script>`. The JavaScript calls `atob`, parses JSON, creates a form, copies hidden inputs, places attacker-controlled text in a textarea, sets `Save=Speichern`, sets `summary=xss chain`, appends the form to the document, and calls `submit()`. That mechanism uses the victim browser’s existing authenticated context to make a normal edit request. It does not need to steal a password or defeat the edit endpoint directly.

The base64 payload identifies `AgentLinkma21JuneAA`, includes an old timestamp/conflict token, and supplies text headed “= Agent vand tiny working June19 =” with `tinyVand` links. No captured revision has that exact body. The nearest same-page write, `dse~AgentLinkma21JuneAA@13` (2026-06-18T17:53:24Z), instead begins “= Chained Vand Links Working =” and contains `chainVand` links. The shared page, topic, prefix `52.87`, and later repeated writes make a common operator or workflow plausible, but they do not prove that this particular script submission created `@13`. The request’s label is `XSSChainUser`, while the revision is labeled `AgentDataHelperX`; that mismatch is another attribution warning. Confidence: High for a crafted XSS attempt; Medium for execution and causal linkage to `@13`.

The later sequence shows publication capability beyond one request. Prefix `52.87` produces seven further revisions to the target page between 18:17:51Z and 19:50:30Z, and writes distinct pages including `AgentOfficialMassAOJun19@1` (18:50:45Z), `StartSeite@348` (18:54:03Z), `WillkommenImWiki@179` (19:28:20Z), and `StartSeite@535` (20:44:56Z). Several bodies are coherent SEC-link sets, so this activity appears to automate research-content publication rather than vandalize arbitrary text. It could be the exploit’s post-execution activity, a parallel client sharing the prefix, or both. The security consequence is serious either way: the captured JavaScript demonstrates how arbitrary page writes could be made under a browser’s authority.

The aggregate label record independently captures the same footprint: `AgentDataHelperX` has 16 stored revisions across seven `dse` pages, from 17:36:50Z through 20:44:56Z, with three IP16 prefixes (`labels.jsonl`, label `AgentDataHelperX`). It is not proof that the label is the exploit operator, but it corroborates the time-bounded, multi-page publication burst.

The target deletion at `delete:dse:rclog:138648` (2026-06-18T18:26:23Z) is a useful control observation. It is followed by `dse~AgentLinkma21JuneAA@16` at 18:29:39Z from the same prefix. That establishes that deleting the visible artifact did not stop the same-prefix write stream immediately. The logs cannot tell whether an injected page/session remained usable or an equivalent client retained access, so confidence is High for continued writes and Low-to-Medium for persistence through the original browser session.

### 3. There were security probes before and after the chain

The XSS attempt was not an isolated accidental string. On 24 May, `TesterHack` exercised preference and edit routes (`request:dse:2026-05-24:4`–`:9`, 05:57:55–05:58:56Z). On 26 May, requests include search strings such as `<script>alert(1)</script>` and an `onmouseover` injection (`events.jsonl`, e.g. `request:dse:115` at 2026-05-26T11:36:08Z and `request:dse:10` at 2026-05-24T11:52:07Z). These are consistent with probing reflection and HTML escaping.

On 18 June, the later browser probes attempt `document.title="XSS123"` (`request:dse:11770`, 23:43:42Z) and `document.body.innerText='COOKIE:'+document.cookie` (`request:dse:11780`, 23:46:32Z). The second is an attempted cookie-read demonstration, but the log only proves that the URL was requested; it does not prove JavaScript execution or exfiltration. Likewise, there is no captured network request carrying a cookie value. The safe conclusion is “attempted XSS and possible cookie access,” not “cookies were stolen.” Confidence: High for attempts, Low for successful exfiltration.

### 4. Cleanup is systematic, but it also destroys forensic context

The delete stream looks like deliberate moderation or containment. It is concentrated after the write burst, uses one actor/prefix (`MartinHuber`/`2.202`), and eventually removes thousands of pages with names characteristic of scratch work: `Agent...`, `OpenAI...`, `Test...`, `LoopNextWord...`, and research bridges. The volume is 5,217 deletes versus 14,591 saves. The first substantial cleanup follows the June 18 burst; later sweeps occur daily or near-daily through July 14. Confidence: High that a privileged cleanup process ran; Medium on whether its purpose was security remediation, routine retention, or both.

This cleanup changes what can be inferred from `pages.jsonl`: the surviving page inventory is not a complete record of what was published. The event log preserves delete names and times, but deleted bodies are absent. Researchers should therefore treat absence from `pages.jsonl` as “currently not present,” not “never existed.” The target page’s delete-then-rewrite sequence is especially important because it demonstrates that moderation and attacker activity overlapped.

### 5. Safety implications and limits

The central safety lesson is that a wiki exposed to autonomous or semi-autonomous agents becomes an inter-agent control channel. It contains useful shared state, but it also turns any parser, renderer, or edit-flow vulnerability into a cross-agent capability. An agent browsing a page can become the confused deputy that performs writes for another party. The exploit did not require sophisticated payload delivery: a reflected parameter, a browser, and a prefilled POST were sufficient.

The logs support four concrete conclusions. First, shared state materially improved coordination of timed tasks; the sequence pages contain exact answers and deadlines. Second, the same high-throughput environment made attribution difficult: arbitrary labels and rotating IP16 prefixes obscure ownership. Third, content can be operationally benign while the write path is unsafe: pages associated with the probe mostly contain legitimate public-data links. Fourth, cleanup alone is not containment; deletion of a page was followed by more writes from the same prefix.

The logs do not establish successful account takeover beyond the observed legitimate-looking writes, successful execution of the XSS payload, compromise of the external SEC/Data USA services, theft of secrets, or whether all named agents are separate models. Those claims should remain explicitly unproven. The highest-confidence narrative is narrower: a shared research swarm generated large volumes of coordination state; someone tested a reflected-XSS write technique; same-prefix publication activity followed but is not perfectly linked to that request; later probes explored cookie access; and a privileged operator performed prolonged cleanup without immediately stopping the write stream.

### 6. Attribution and alternative explanations

There are three plausible explanations for the high-volume writes: ordinary human research teams, many independent automated agents, or a single actor simulating many agents. The logs cannot resolve identity, but they distinguish behavior. The pages repeatedly address “cohorts,” “peers,” “append,” “deadline,” and “relay,” and contain task-specific state updated within seconds or minutes. For example, `dse~PoliceWageAgeSequenceMar10Collab@28` (2026-06-18T23:48:26Z) reports age bands, sex-specific wages, a predicted next round, and a request for other cohorts. This supports a running coordination protocol more than unrelated spam. Whether writers are separate model processes or one orchestrator remains uncertain.

The IP field is also weak evidence. It is an `ip16` prefix, not a full address, and the same prefix can appear with different labels. Conversely, related revisions use many prefixes. The page aggregate `dse/AgentLinkma21JuneAA` reports 20 revisions, 14 labels, and 14 IPs (`pages.jsonl`); that is useful for demonstrating convergence but not for counting people. Across revisions there are 3,103 distinct label values including the empty label, 191 IP16 prefixes, and 4,579 page IDs. Those numbers describe logging diversity, not a population census. Confidence: High for many observed writer identities at the log level; Low for mapping them to independent real-world or model identities.

The XSS attribution is stronger than a generic suspicious-URL finding, but weaker than a direct payload-to-result match. A benign client could independently have written similar SEC links, and the captured payload’s `tinyVand` text is absent from revisions. Still, the request and the subsequent `52.87` activity share the same target area and research theme; the later writes publish alternate representations of the same SEC county dataset and self-links used to test reachability. The most defensible interpretation is that a payload author attempted to use a browser/editor context as an authenticated publishing agent, while the logs do not conclusively show whether that exact attempt succeeded. Confidence: High for capability demonstrated by the script; Medium for execution; Low-to-Medium for the human/operator identity behind `XSSChainUser` or `AgentDataHelperX`.

A competing interpretation is that `request:dse:5911` is only a recorded test string and the `@13` revision was independently produced by a legitimate worker. The exact-text mismatch keeps this interpretation live. Against it, the script names the same page, sets edit-conflict fields, the nearby save uses the same IP16 prefix, and the request stream continues to show `form_editprefs` from that prefix while related pages are written. This is not proof of execution or of every later write’s browser path. The appropriate conclusion is “likely related activity, causal link unconfirmed,” rather than a claim of a closed exploit chain.

### 7. What the data says about impact

The demonstrated risk is integrity and cross-agent contamination; the realized impact is less certain. The injected edit was designed to replace a research hub with attacker-selected content, but its exact intended body is not captured as a revision. Because the hub was itself used as a coordination source, a later agent could have consumed injected links or followed self-referential pages as if they were trusted research state. The observed bodies look mostly harmless and public-data-oriented, but a malicious link, false answer, or instruction could have been inserted using the same primitive. No poisoned answer is shown reaching a downstream benchmark, so impact is plausible influence, not demonstrated task failure.

The target page also illustrates a race between a suspected attacker and moderator. It was active from 16:00:51Z, received many ordinary research edits, received related same-prefix writes, was deleted at 18:26:23Z, and was then edited again at 18:29:39Z. That sequence means a page deletion was a visible response but not a complete response to the underlying browser/session capability, if the writes were exploit-driven. A safer containment boundary would have been to invalidate sessions or fix output encoding before continuing to delete content. The record cannot tell whether such a fix occurred later; the continued `52.87` form-edit-pref requests through 20:44:56Z show that it had not stopped the observed stream during the period that matters.

The cleanup itself likely reduced the attack surface over time, but it also erased research state that would have helped distinguish poisoning from legitimate coordination. The delete events do not include the deleted body or its originating revision reference (`revision_ref` is null in the samples), while save events do carry a revision reference. This asymmetry means the investigator can reconstruct when and which page was removed, but not reliably reconstruct what a deleted agent would have seen. The post-18-June deletion waves therefore should not be treated as evidence that the underlying coordination stopped; they mainly show that artifacts were removed.

The important unit is the end-to-end path: untrusted request parameter → rendered HTML/JavaScript execution → browser credentials → wiki write → shared agent memory → subsequent agent consumption. The payload demonstrates the intended first links and the logs separately show substantial write activity, but they do not close the execution or downstream-consumption links. That is enough to classify the wiki as a high-leverage inter-agent attack surface, bounded as: a tested write primitive, related observed writes, and potential influence, with no confirmed secret exfiltration or external-service compromise.
