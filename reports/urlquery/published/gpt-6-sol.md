# TL;DR

The collection is dominated by repeated browser scans of data sources and rendering intermediaries in April–June 2026. The strongest visible pattern is iterative attempts to reach structured data and images through ordinary sites, direct API URLs, mirrors, URL converters, Base64 HTML carriers, and CORS proxies. Many scans end in browser error pages, anti-bot challenges, or content that cannot be inspected in this download. Successful HTTP responses are therefore evidence of a resource being served, not proof that a desired dataset was obtained or exfiltrated. The evidence supports several related exploration episodes, but submission identities are unauthenticated and the collection does not establish one actor or motive.

## Evidence and scope

The supplied files contain 38,158 downloaded scans, against 38,160 catalogued scans; two are acquisition gaps. They are selected observations rather than a census. Scans retain distinct submitted, initial, and final URLs; transactions retain order within each scan. The destination IP identifies the scanned destination, not a person. Most scans date to April–June 2026; the largest initial-domain groups are `unctad.org`, `httpbin.org`, `thrill-data.com`, `aihw.gov.au`, and `whssgr.com` [manifest.json; scans.jsonl]. This distribution establishes where browser scans were pointed, not who submitted them or whether their aims succeeded.

## Episode 1: sustained attempts to query UNCTAD data

From April 13 through September 9, 2026, 13,268 scans started on the `unctad.org` domain family. The heaviest activity fell in late April through June. The URL paths show a structured search of the UNCTADstat interface: `api/reportMetadata`, `api/report-files`, `datamart-api`, `bulkdownload`, and the public `datacentre/dataviewer`. Within the datamart path, repeated series include PCI, trade in processed food, trade in services, ocean services, port calls, and gender related industries. Query strings vary `$top`, `$select`, `$filter`, `$orderby`, economy codes, years, culture, and a repeated subscription key. These are concrete indications of trying multiple API routes and query shapes, but they do not identify who held the key or whether it was authorized [scans 6a5cfd89-611f-472d-a96d-7cbbfe7c2a15, 2f852efc-dd80-4279-8351-0578711d5a36, 16d51563-c474-40a0-8dfb-6f3a6647521a, 3596d486-f565-4a67-b69c-de7669def1bf; initial_url.addr].

The outcomes varied sharply. For initial UNCTAD-domain requests, 5,552 recorded HTTP 400, 2,778 recorded 404, 4,323 recorded 200, and 468 had no recorded status. For example, a PCI `Facts?$top=1` GET returned 400, whereas a PCI `Economy` GET with a subscription key returned 404 [scans 2f852efc-dd80-4279-8351-0578711d5a36 and 254148d4-bef9-4b4e-ab03-b5e0240f7d59; http[0].url.addr, http[0].response.status_code]. This mix is inconsistent with either universal access or universal blocking. It is compatible with parameter mistakes, nonexistent routes, service behavior that varies by endpoint, or access controls. The downloadable record usually does not contain the API response body, so a 400 cannot be diagnosed more finely and a 200 cannot by itself prove that a complete requested table was read.

The more distinctive mechanism is browser-mediated POSTing. A submitted `httpbin.org/base64/` URL decodes to HTML with a form targeting UNCTAD's plastics-trade `Facts` route. The recorded browser first loaded that HTML with GET 200, then sent a POST to the API and received HTTP 200 with an OData JSON content type. The POST body is recorded locally as `http[1].request.post_data`; the API response has a positive reported size but is marked unavailable here [scan 6a0a9eaf-a3da-434e-bf3d-780330d247a8; submit.url.addr decoded_text, http[0–1].request.method, http[1].response.raw, resources source_field `http[1].response.data`]. This demonstrates a real form submission and API response, but the absent response bytes limit claims about its contents. Another Base64 form reached a Tableau `startSession` route by the same method in a later, separate data episode [scan bfff80df-d9e0-417a-a1a9-546421b182c1; http[0–1]].

A second HTML carrier used `fetch` against the UNCTAD gender-industries `Facts` route and attempted to report the result through an image request to `webhook.site`. The browser recorded a POST 400, followed by a GET to the webhook with `err=TypeError: NetworkError when attempting to fetch resource`; the webhook request itself returned 200 [scan 1464ce67-45c1-4cf9-8f01-51a11d681ba1; decoded_text source_field `submit.url.addr`, http[0–2]]. Here the observable leak was an error message in a URL, not a demonstrated leak of UNCTAD data. The design would have sent up to 1,200 characters of response text if the script's success branch ran. This difference matters: the program expresses an intention or test to move response text to another endpoint, while this scan records the failure branch. A repeated subscription key in submitted URLs is a visible credential string, but its presence alone does not establish misuse or data extraction.

## Episode 2: inaccessible history site and converters

Between May 10 and 13, 1,644 scans started at `whssgr.com` or its mail and www subdomains, often repeating `/history/`. All 1,644 first transactions had no recorded HTTP status. Final states were 1,183 Firefox problem pages and 461 private-browsing pages. A direct request to `mail.whssgr.com/history/` ended in a timeout page; another to `whssgr.com/history/` ended at `about:privatebrowsing` [scans 72523175-b552-42f8-90ff-f7f3309ca81b and 6d2b0933-f2f2-43cf-a366-a925bfdde8ca; initial_url.addr, final_url.addr, http[0].response.status_code]. The records therefore support repeated unsuccessful browsing of that history path, not reading its page content.

The same target appeared through intermediaries. `markdown.new/whssgr.com/history/` and variants with an explicit `https://` target recur among 1,001 scans initially on `markdown.new`. An example converter request returned HTTP 200 with `text/markdown`, yet the scan's final page was `about:privatebrowsing`; no reliable history content is established by that status [scan 7021162a-2ae3-4760-b162-d76cff8a44db; initial_url.addr, http[0].response.raw, final_url.addr]. Among initial `markdown.new` scans, 435 first transactions returned 429, consistent with rate limiting. Multiple spellings and converter forms suggest attempts to obtain a readable representation despite browser failures. They could also be automated link checking or a normal researcher's repeated retries; the submission record does not supply a trustworthy intent statement. A separate May 26 cluster used the converter on `portal.max.gov` budget PDF paths, showing that `markdown.new` was a general reading method rather than unique to the history site [scan 94424646-9fcb-4ecb-8adf-487ec082b6a5; initial_url.addr].

## Episode 3: ride-wait data and the difference between site noise and purposeful requests

Some 3,694 scans started at `thrill-data.com` between October 2025 and July 2026. The repeated paths point to Disney attraction and Lightning Lane pages, graph endpoints such as `/waits/graph/quick/ridell`, and differing date, ride, and output parameters. One graph GET for a ride ID and December 30, 2022 returned HTTP 200 with `application/json` [scan aee6431b-77ef-4605-9e51-55949490fec6; http[0].url.addr, http[0].response.raw]. This is stronger evidence of a data-bearing endpoint being reached than a generic HTML 200, although the JSON body itself is unavailable in this download. Other scans received 404 or 500, and repeated query variations appear in the submitted URLs [scans 1c515fee-476f-4553-9ea7-034151f8434c, 92d9349a-1511-4e0f-9606-cedaafc0ba0d, 4a5d5bb4-2a87-4511-b823-73e21f2dcb39; initial_url.addr].

This group generated many ancillary requests: across these scans, 14,420 POSTs and 9,173 OPTIONS transactions were recorded, but most POSTs went to advertising or other third-party hosts, including `stay22.com`, `spellknight.com`, and `html-load.cc` [http.jsonl grouped by initial scan domain, request.method and url.domain]. Counting all such traffic as deliberate submissions by the scan requester would be misleading. Browser scans load scripts, ads, and analytics as well as requested pages. The first-request status was 200 in 3,361 of the 3,694 scans, yet this count says little about whether a precise historical graph was extracted. The repeated path and parameter selection is the stronger evidence of an attempt to retrieve that data.

## Episode 4: Australian health dashboards, images, files, and instrumentation

Activity shifted heavily to the Australian Institute of Health and Welfare in May–June: 2,731 scans began on `aihw.gov.au` subdomains. Targets included PBS prescription data ZIP files, Tableau dashboards, PNG/PDF exports, and a mental-health-in-aged-care view. The requests used filters such as state, local government area, medicine class, age group, and measure, plus Tableau embed parameters. This looks like efforts to obtain tabular values or rendered dashboard views, but the record cannot tell whether this was one project or several [scans 3e6722f9-fd60-40bb-b159-ace1626916e7, 4188e2ae-28dc-4318-be56-4671d58fd1f8, c89499f5-e3b7-4ae3-bcf2-3e5bdee8c29d; initial_url.addr].

Access conditions were mixed. Initial AIHW-domain transactions recorded 1,293 HTTP 200, 478 HTTP 403, 222 partial-content 206, 62 range errors 416, and 516 with no status. A ZIP-file scan ended on a `Just a moment...` page; its recorded early traffic includes a 403 on a favicon and POSTs to the site's challenge platform. These are signs of a challenge flow, not proof of downloading the ZIP [scan 3e6722f9-fd60-40bb-b159-ace1626916e7; title, http[0–2].url.addr and response.status_code]. A PNG export scan instead ended at a DNS error with no recorded HTTP status [scan 4188e2ae-28dc-4318-be56-4671d58fd1f8; final_url.addr, http[0].response.status_code]. A form-based Tableau session did receive POST 200 JSON at `startSession`, but this establishes session initiation rather than retrieval of dashboard figures [scan bfff80df-d9e0-417a-a1a9-546421b182c1; http[1]].

The custom instrumentation is particularly visible. Decoded `httpbun.com/base64/` HTML loaded Tableau's JavaScript API, created a view, logged states such as `SCRIPT`, `INTERACTIVE`, sheet name, and parameters, and encoded those messages into `httpbun.com/status/204?log=` image requests [scan 10a79188-cbcf-4eb1-ba51-de502a716f46; decoded_text source_field `submit.url.addr`]. In that individual scan, the recorded transactions show only the carrier page and Tableau script; no `log=` request or view session was observed [same scan, http[0–2]]. The program is a diagnostic attempt, not evidence that parameters were obtained. Another wrapper did create a Tableau session and sent an object-description JSON string to `example.com/OP?d=...`; that GET returned 404, but the request URL demonstrates that browser-visible object metadata was placed in the query string [scan ba1b149e-2dc8-4329-ba7b-9989e2c83e80; decoded_text source_field `submit.url.addr`, http[0], http[3]]. The destination is the example domain and the visible data describe Tableau objects, so this is not evidence of patient records or a successful transfer to a controlled mailbox.

## Episode 5: a small, concrete mail API sequence

A short June 19–20 sequence is distinct from the public-data searches because it includes a supplied email address, password, and later bearer tokens. The report deliberately omits their values. A Base64 HTML page submitted a cross-origin POST to `api.mail.gw/accounts`; the recorded response was 201. A following GET to `httpbun.com/status/204?log=` included the reported 201 and a prefix of an account JSON object, and returned 204 [scan 3d4b0181-3d32-413a-853d-b2a7a40604c0; decoded_text source_field `submit.url.addr`, http[1], http[4].url.addr]. The 201 and returned account identifier are good evidence that account creation succeeded in that scan, although the account's ownership and intended use are unknown.

Two later wrappers submitted credentials to `api.mail.gw/token` and recorded 200 responses. Each also sent a `TOKEN` log URL to `httpbun.com` containing the beginning of the token response. The HTTP transaction order in the file is not a guaranteed causal order for concurrent browser requests: some logs appear before the carrier-page transaction in the original indexed order. The combined submitted script and recorded requests nevertheless show the token response was placed into a URL and requested from a second host [scans 6125f779-b94e-40cd-b544-3eb7914c4b0e and f3e0ef3c-a8a4-48d2-993d-f83363282c94; decoded_text source_field `submit.url.addr`, http[0–6].url.addr, response.status_code]. That is more consequential than merely embedding a token in submitted HTML: it is an observed cross-host request carrying response material. The `httpbun` 204 acknowledges the request, but no evidence here shows who could read its logs.

A subsequent carrier sent a bearer-authenticated GET to `api.mail.gw/messages`. The API returned 200, and a `httpbun.com/status/204?log=` request contained a JSON collection with `hydra:member:[]` and `hydra:totalItems:0` [scan e6b5c7bc-41c9-4937-a941-cdaa7019fd2e; http[0].url.addr, http[2].url.addr, response.status_code; decoded_text source_field `submit.url.addr`]. This demonstrates a response was observed and logged, but the visible list was empty; there is no basis to claim message content was retrieved. A later account-creation attempt returned 422 with a constraint-violation response, followed by another token request returning 200 [scans bfea2b71-b931-40a9-84b9-db7a6a15c7a9 and 15c7478d-d066-406e-ac54-f5c98c421fca; http[1–4] and http[0–3]]. The apparent continuity comes from repeated API paths and account material in the submitted programs, not authenticated actor identity.

## Other visible searches and what they add

The Mapillary cluster illustrates a similar API-search pattern without the same observable side effects. Between June 10 and 17, 633 scans started at `mapillary.com`, commonly using `graph.mapillary.com/images`, bounding boxes, fields such as `computed_geometry` and `captured_at`, image IDs, and access-token query parameters. One sample ended at Firefox's DNS error without a status; other first responses in this cluster include 351 HTTP 200, 136 HTTP 500, 134 without status, and 12 HTTP 400 [scan b2f7f2b3-6f28-438b-adbc-3d1de8bd3abd; initial_url.addr, final_url.addr, http[0]; scans b2f7f2b3-6f28-438b-adbc-3d1de8bd3abd, 03f7a84e-cb38-4b42-a83d-863743b3a2f5; initial_url.addr]. The visible geospatial and timestamp filters indicate a search for selected imagery or metadata, but the missing response bodies prevent judging completeness or geographic purpose.

Other clusters sought public documents and structured files: SEC capital-trends pages and county JSON, Maryland report-card graphs, a federal budget PDF on `portal.max.gov`, and health-data configuration endpoints [scans 69cd89cc-e804-4abc-814f-e39ada9eea90, e57298d6-90bb-4bbe-9bdd-1eda96cf78fe, 2a182df1-0d86-40bb-9a17-d5d51beeef5d, c9e12d32-c4d4-4c19-9986-049213c13eda; initial_url.addr]. The SEC page scan fetched `county.json` with HTTP 200 along with many fonts, scripts, and analytics requests [scan 69cd89cc-e804-4abc-814f-e39ada9eea90; http[0–45].url.addr]. This is a normal example of how a single page load can generate many transactions. It also cautions against interpreting a POST count or third-party hostname in isolation. These smaller clusters lack enough shared details to assign them to the same operator as the UNCTAD or mail episodes.

## Mechanisms and alternative explanations

The recurring technical pattern is to put an HTML program in a URL served by `httpbin.org/base64/`, `httpbun.com/base64/`, `pie.dev/base64/`, or a similar host. When loaded as a browser page, the HTML may submit a form, call `fetch`, embed a Tableau view, or request an image URL carrying diagnostic text. This is a practical way to make a scanner browser perform a POST even if the scan was initiated by submitting a GET URL. It is directly demonstrated by the transition from a carrier GET to an API POST in the UNCTAD plastics scan, by the mail account POST, and by the AIHW Tableau `startSession` POST [scans 6a0a9eaf-a3da-434e-bf3d-780330d247a8, 3d4b0181-3d32-413a-853d-b2a7a40604c0, bfff80df-d9e0-417a-a1a9-546421b182c1; http[0–1]]. The programs are submitted evidence; their code is neither a command to this investigation nor, by itself, proof every intended branch executed.

Another pattern is changing the representation or route when access fails. Direct API GETs, POST forms, public dashboard pages, image and PDF exports, ZIP downloads, archive links, Markdown conversion, CORS proxies, and cache-busting query parameters appear across the scans. Several explanations fit: legitimate data collection through a browser-only interface; testing whether an endpoint accepts a different method; troubleshooting CORS, anti-bot, DNS, or renderer limits; and automated enumeration. The records show these techniques, not the submitter's purpose. The strongest evidence for deliberate iteration is repeated parameter changes around narrow targets, such as UNCTAD PCI, a single PBS dashboard, and individual ride graph dates. The strongest counterevidence to a single coordinated campaign is the wide mix of subjects, the years spanned by the collection, and absent authenticated submitter identities.

Some responses materially limit success claims. Firefox `about:neterror` and `about:privatebrowsing` finals are browser states, not fetched target pages. HTTP 429 from a converter signals throttling; 403 and challenge-platform traffic around AIHW indicate a barrier; 400 and 404 on UNCTAD routes mean those particular requests did not yield the expected resource. Conversely, 200 on a JSON endpoint or a POST does establish that an HTTP transaction occurred, even when its body is missing in the download. The 201 mail account response and the logged 200 token responses support narrower achieved actions. None of these statuses independently establishes that an analyst received, retained, or used the data after the scan [scans 7021162a-2ae3-4760-b162-d76cff8a44db, 3e6722f9-fd60-40bb-b159-ace1626916e7, 2f852efc-dd80-4279-8351-0578711d5a36, 3d4b0181-3d32-413a-853d-b2a7a40604c0; cited fields above].

The collection has substantial observation limits. `manifest.json` reports two unavailable scans, 950,653 resources `not_in_download`, and 365,882 `not_available`; embedded content is only a fraction of resource metadata. These categories have different meanings. A positive-size script with no data is missing from this evidence, not an empty script; absent HTTP content cannot turn a reported 200 into confirmed semantic success. Encoded or decoded text can expose what a submitted program *would* attempt, while the ordered HTTP records show what the browser was observed requesting. URL redirects are distinct from submitted and initial URLs, and the scanner destination IP is not a source-actor address [README.txt; manifest.json; scan 6a0a9eaf-a3da-434e-bf3d-780330d247a8, initial_url.addr versus final_url.addr].

The selection also distorts apparent prevalence. These are recorded web scans, with duplicate URLs intentionally retained, and one submission-user field value appears on 33,104 of the 38,158 downloads while 5,054 lack one. That field is submission metadata rather than an authenticated personal identity. Dense day clusters and duplicate exact URLs may reflect a single workflow, resubmissions, or collection choices. The earlier isolated 2023–2025 scans and sparse unrelated domains should not be collapsed into the 2026 data-query episodes solely because they sit in the same files. Within a scan, third-party scripts can create traffic on their own, as the SEC and ride-site examples show. No supplied evidence gives the full history of site availability or what happened outside the scans [scans.jsonl submission_user_id, scanned_at; scan 69cd89cc-e804-4abc-814f-e39ada9eea90; http[0–45]].

## Synthesis

The most defensible account is repeated exploration of data interfaces, often using browser-carried HTML to submit requests and log short results when direct viewing was unreliable. The UNCTAD and AIHW episodes show real POSTs and mixed barriers; the history-site episode shows repeated failure and converter retries; the ride and Mapillary clusters show narrowly parameterized data searches. The mail sequence shows a created account, token-bearing log requests, and an empty message listing. These are observed outcomes, not a warrant to infer the submitter's identity, authorization, eventual data holdings, or a common motive across all topics. Where content is absent, a status code or final title must remain a bounded observation rather than a reconstructed result.

## Further verification: dashboard access

A more direct AIHW test is especially useful counterevidence. A submitted HTML wrapper called Tableau API methods on named worksheets, including `getUnderlyingDataAsync`, `getSummaryDataAsync`, `getSelectedMarksAsync`, and `getDataSourcesAsync`, then sent method results or exceptions in `httpbun.com/status/204?log=` image URLs. The recorded URLs repeatedly carried `NO` and `PermissionDeniedException`, with status 403 for the underlying-data, summary-data, selection, and schema operations; the associated Tableau session request also recorded 403 [scan e6ab8b31-b0df-408d-95bf-f533114cf865; decoded_text source_field `submit.url.addr`, http[0–1], http[45], http[53], http[56], http[59], http[61], http[64], http[71], http[83], http[91], http[96–97]]. That scan shows the JavaScript API could expose method names and errors while denying the requested rows. It therefore narrows the significance of the other Tableau 200 session responses.

At the same time, some diagnostic logs carried object names, filter names, positions, and parameter values rather than errors. For example, one reported a `parameterControl` object with coordinates; another reported a filter list including medicine and local-area names [scans 5ac572b4-aad6-4b25-9c27-df460dd8cb89, 9f404281-67c0-43f5-9762-3c6cf99ed010; http[2–3].url.addr and http[63].url.addr]. Across the collection, 1,774 recorded requests used the `httpbun.com/status/204?log=` pattern, 1,761 of which returned 204; the number includes diagnostic messages of many kinds and must not be read as 1,774 successful data extractions [http.jsonl, url.addr and response.status_code]. Such URLs can transmit metadata simply by being requested, regardless of whether the destination shows a page or the browser can inspect the response. They also reveal the diagnostic nature of much of the activity: short labels, timing tests, error messages, and API object descriptions are frequent alongside attempts to read values.

The browsers' response to an encoded carrier depends on both the carrier serving HTML and the target permitting the request. A form submission navigates to the target and may succeed despite script-reading restrictions; a cross-origin `fetch` can send a request yet fail when code tries to read its response. That distinction matches the UNCTAD form's observed POST 200 and the separate fetch example's POST 400 plus network-error log [scans 6a0a9eaf-a3da-434e-bf3d-780330d247a8; http[0–1]; 1464ce67-45c1-4cf9-8f01-51a11d681ba1; http[0–2]]. The evidence does not isolate CORS as the sole cause of the latter error, but it explains why a target transaction and a failed browser script can coexist.

## Conclusion

The strongest confirmed effects are specific browser requests and responses: UNCTAD and Tableau POSTs, a mail account creation, token responses logged in URLs, an empty mail collection, and Tableau methods denied by 403. Repetition around narrow public-data targets makes deliberate exploration plausible. The large number of broken, challenged, or bodyless scans limits any stronger claim about complete datasets, later use of returned material, or common control of the separate episodes. The logged token prefixes are the clearest observed transfer of sensitive response material to an intermediary host; the available record does not identify its reader or establish a further compromise.
