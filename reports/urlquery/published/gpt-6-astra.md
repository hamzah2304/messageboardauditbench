# Investigation of the recorded web scans

## TL;DR

The strongest pattern is repurposing a web scanner as a remote browser for data retrieval: encoded HTML launches requests, submits forms, embeds dashboards, and exports results through titles, outgoing URLs, or intended image encodings. Some actions demonstrably ran; many failed or lack response bodies. This dominates the 2026 material and does not, by itself, establish intrusion.

Separate consequential episodes include November 2023 Microsoft-themed phishing infrastructure, attempts to create scanner accounts and API keys from scanned pages, and September 2026 probes against a cryptocurrency ramp. The payment probes reached sensitive endpoints but do not demonstrate authentication bypass, wallet modification, or completed transfers. The records support several activity clusters, not a single identified actor.

This is a selected collection with substantial missing content. Findings below distinguish submitted code, observed requests, and demonstrated results; credentials are deliberately omitted.


## Scope and interpretation

The manifest lists 38,160 catalog entries, 38,158 downloaded scans, and two acquisition gaps. Downloaded scan timestamps span September 22, 2023 to September 20, 2026. April–June 2026 account for 37,241 scans, approximately 97.6% of the collection. These are counts of observations, including repeated URLs, not counts of victims, actors, or successful operations. The concentration is a strong selection effect: this archive cannot establish the prevalence of these behaviors across the wider web. [manifest.json: catalog_count, downloaded_count, missing_count; scans.jsonl: scanned_at.]

I compared scan metadata, decoded URL text, raw transactions, and available content. Citations use the original scan identifier followed by transaction indices or source fields. Decoded text supplies a readable view of encoded evidence, not proof that the text executed. Transaction indices identify records; where ordering matters, recorded `at` values and request relationships are preferable to assuming indices form a causal timeline. No recorded program was executed, request replayed, credential used, or outside site contacted.

Missingness sharply limits outcomes. The manifest reports 46,516 embedded resource entries, 48 embedded-empty entries, 365,882 unavailable entries, and 950,653 not downloaded. Those categories are resource records, not unique sites or files. In particular, many HTTP response bodies and JavaScript bodies are absent even when metadata records a positive size. A page title, HTTP 200, or available-upstream flag cannot substitute for the missing content. [manifest.json: resource_availability; README.txt; e.g. scan 960b3314-f644-4832-a57e-fab108a95678, http[46].response.content.]

## The dominant mechanism: scans as programmable browsers

The leading initial-domain counts are UNCTAD, 13,268; httpbin.org, 5,898; Thrill Data, 3,694; AIHW, 2,731; and whssgr.com, 1,644. Additional echo services, proxies, and rendering services recur, including httpbun.com, eu.httpbin.org, markdown.new, and jina.ai. These counts classify `initial_url.domain`, not every destination contacted. An echo-service starting URL can contain a program targeting an entirely different organization. Treating these domains as a list of compromised sites would therefore misdescribe the evidence. [scans.jsonl: initial_url.domain, all downloaded rows.]

The repeated construction is an HTML document encoded into a `/base64/` URL. When a compatible service returns it as HTML, the scanner browser can run its script. The document issues `fetch` requests, submits a hidden form, loads a visualization library, or navigates elsewhere. Its author can arrange for outputs to appear in the scan's title, DOM, final URL, or transaction log. Across the convenience decoding file, 8,030 distinct scans have at least one decoded row containing `<script` in a case-insensitive search; this is a reproducible indicator, not an exact execution count. Repeated source fields inflate row totals, and some decodings are partial. [decoded_text.jsonl: text, scan_id.]

A particularly clear example is the April 29 UNCTAD PortCalls query. The encoded page creates a POST form selecting Year, Economy code/label, and measure M3762, with filters for 2022, commercial-market code 05, and economy code 842. Its script calls `f.submit()`. The transaction record contains the initial echo-service GET and then a POST to the specified Facts endpoint, with a matching form-encoded body and HTTP 200. Thus the browser performed the requested query submission. The actual answer is not supplied, so neither the returned values nor the query's semantic correctness can be verified. [scan 2fedcab0-5d3a-47ae-b5e6-e97750e4b2a0, decoded http[0].url.addr; http[0–1]; http[1].request.post_data.]

This mechanism explains why POST-oriented data services recur beside apparently unrelated echo hosts. Cross-origin form navigation can send a conventional form without giving the initiating script access to the response. A JavaScript fetch has a different constraint: cross-origin response access depends on browser CORS rules. Other examples explicitly use `mode:"no-cors"`, proxy services, or output navigation to work around practical retrieval limitations. These are evidence of attempts to adapt the browser workflow, not proof of defeating the target's authorization. Subscription keys embedded in URLs show possession or copying of a key; their presence alone does not establish theft, private access, or identity. [scan bd3d04cb-1bee-42c5-a1fa-8392c9735f85, decoded javascript.script[0].url.addr.]

A May 10 Thrill Data experiment takes the approach further: it requests a historical attraction page through AllOrigins, inserts the returned HTML into a hidden element, replaces `Plotly.newPlot` with a capture function, and evaluates embedded script text to collect plotted traces around specific morning times. The observed proxy GET returned 200, and the scan also loaded Thrill Data assets and third-party scripts. That supports retrieval and page processing, but the requested numerical trace output is not available here. The captured page's analytics activity is a competing explanation for some secondary traffic: not every downstream request was explicitly authored by the experimenter. [scan dc7d4791-4cee-479c-8a78-32f7645ca5c7, decoded javascript.script[0].url.addr; http[5], http[4].request.post_data, http[32].request.post_data.]

## Data extraction and output channels

The June AIHW experiments demonstrate a more consequential result than merely loading a page. One encoded page embeds the public PBS Tableau dashboard and calls `getFiltersAsync()` on worksheet `Text-ATC1-script`. It serializes filter names, types, and selected values, then navigates to an example.com URL carrying those results. The scan records a POST to Tableau's `get-filter-info` command and an outgoing GET containing JSON with fields including `Atc2`, `Select ATC1 medicines`, and their applied values. This demonstrates that dashboard metadata reached an externally addressed request, even though that receiving URL returned 404. A successful receiving page is unnecessary for the scan log to retain the query string. [scan 4f27ea2f-0865-4ab2-b7bd-be4d794ae2d1, decoded submit.url.addr; http[15–16].]

The proper claim is metadata extraction from a public dashboard, not theft of individual health records. The program names a public workbook, and the observed output concerns filters. A 404 at the output destination is not evidence that the preceding extraction failed; equally, the appearance of an external host does not prove that an attacker controlled it or subsequently retrieved its server logs. The scanner's own recorded URL is already an output channel.

A different program queries Mapillary image identifiers, packs them as bytes, and draws black-and-white blocks onto a canvas sized to the browser viewport. This appears designed to make structured data recoverable from an image capture rather than relying on a downloadable response. The selected scan did make the Mapillary request and received HTTP 200, but its final title was `N0`, matching the program's zero-item branch. The example therefore supports execution with an empty extracted list, not successful recovery of image IDs. The code also defaults to an empty list when the expected `data` field is absent, so `N0` does not uniquely establish an empty geographic search. No screenshot payload was inspected. [scan 0a1c11b7-df72-4c3e-b7d4-acc1234b8b3f, decoded url.addr; http[2]; scans.title.]

There is positive counterevidence to treating all canvas experiments as failures. A related Mapillary scan requested up to 2,000 IDs, received 200, and ended with title `N1609`. Its decoded program sets that title only after packing the returned IDs and calling `putImageData`. This supports successful browser-side processing of a nonempty result, although the underlying IDs and any later screenshot decoding are not independently verified. A separate thumbnail-grid variant loaded image resources and reported `N20`. [scan 143519e1-37a9-40c0-94eb-06412d83cc3b, decoded submit.url.addr, http[1], title; scan 3a5274fb-efb5-4ae4-9dfb-892756974bcb, decoded submit.url.addr, http[0–3], title.]

A contrasting AIHW range-filter program never progressed beyond its initial echo-service transaction in the supplied record. Its code intended to apply a numerical filter and report filter-domain limits, but the scan title is “Problem loading page” and the sole transaction has no status. It illustrates why interesting source code cannot be counted as a completed extraction. [scan 9ec15e90-3c7c-4a48-be2c-79f19b44c764, decoded submit.url.addr; http[0]; scans.title.]

Actual export restrictions also appear. In a June 19 PBS scan, a program tried selected marks, underlying data, summary data, and data-source methods across three worksheets. The underlying-data and summary-data commands returned 403; outgoing diagnostic URLs preserved `PermissionDeniedException`. Ordinary runtime-model requests returned 200 in the same session. This is unusually useful counterevidence: visualization loading worked while specific data-export operations were denied. It would be wrong to interpret the surrounding successful asset requests as proof that restricted data was obtained. [scan e6ab8b31-b0df-408d-95bf-f533114cf865, http[7], http[42], http[44–45], http[53], http[56], http[6].]

Another example makes the transport/application distinction explicit. A UNCTAD Years request returned 200, and a subsequent webhook POST also returned 200. However, the supplied webhook request body is only `ERR TypeError: NetworkError when attempting to fetch resource.` The intended data transfer therefore became error reporting. Browser response-access restrictions are a plausible explanation, but the available error does not uniquely diagnose CORS. This prevents counting a successful HTTP exchange at both ends as successful data extraction. [scan ef8618b6-e23c-4644-bd5a-2b4ef2751d68, http[1], http[3].request.post_data.]

## Attempts to operate the scanning service itself

A related but distinct cluster directs encoded forms toward urlquery.net signup, login, and API-key endpoints. Programs vary disposable-looking email domains, form field names, iframe targets, delays, and navigation to the profile page. These are active account-workflow attempts launched from scanned content, rather than incidental assets loaded while viewing a public dataset. Their relationship to the data-retrieval work is suggested by labels and repeated techniques; it does not authenticate a common operator or establish whether account creation was permitted. [Examples: scan f8d7f443-a153-42fe-a67a-57c495875091, decoded submit.url.addr; scan 51a8b104-6337-4a13-8ff5-96bace96eac0, decoded submit.url.addr.]

The June 14 evidence distinguishes partial progress from the desired outcome. One page submits signup and then requests a new API key. Signup returns 200 with an instruction to redirect to login; the API-key request returns 400 with the explicit header message “Only available to verified accounts.” Another page submits login, receives a 307 with `hx-redirect: /` and a JWT-bearing Set-Cookie header, but its API-key request receives the same verified-account restriction. Thus the records support server issuance of an authentication token and an enforced verification gate, not successful key issuance through these attempts. Credentials and token values are unnecessary to this conclusion. [scan e9d55825-0d74-44f5-9fca-5c2060144252, http[0].response.raw, http[4].response.raw; scan 51a8b104-6337-4a13-8ff5-96bace96eac0, http[1–2].response.raw.]

Token issuance did not invariably produce a usable top-level session. On June 20, a login response again set a JWT, but the subsequent profile GET redirected to `/user/login`. Browser cookie partitioning, cookie acceptance, navigation context, or application session rules could explain this; the record does not isolate the cause. It directly contradicts a blanket claim that a Set-Cookie header proves a persistent authenticated browser session. [scan 255fcb20-19f8-477c-aec8-f62da5258256, http[0], http[5–6].]

A June 21 payload goes further, attempting to submit a fresh URL scan through the public submission API using a recorded API key and a CORS proxy, then forward the answer to a webhook through that proxy. Both proxy POSTs appear and return 200. Their response bodies and submitted-result details are missing, so this demonstrates an attempted recursive workflow, not proven creation of a child scan or acquisition of the key by the preceding signup experiments. Shared technique and nearby timing are insufficient to bridge that evidentiary gap. [scan 21f11efa-e1d4-41fb-9055-83cfbaea5ed6, decoded submit.url.addr; http[0], http[3].]

This cluster also illustrates a concrete exposure mechanism: credentials and keys placed inside encoded URLs remain recoverable from recorded URL fields. Base64 is packaging, not confidentiality. That observation does not authorize using them and does not establish that an unrelated party obtained them.

## November 2023: personalized Microsoft-themed phishing paths

The older records contain a substantially different pattern. On November 13, a URL under woodlandshomesbuyerincentives.com ends in a Base64-encoded recipient email address. The resulting transactions include a POST to a workers.dev address with that recipient in `qrc`, a redirect through a signed-looking token on puchoiswater.com, and a further `/owa/` URL with a matching `login_hint`. Microsoft-style login assets are then requested under the puchoiswater.com origin, alongside genuine Office 365 resources. This is strong evidence of a personalized login interception or imitation flow; the token's JWT-like structure does not validate its signature or establish who issued it. [scan 56927d26-04fc-4859-8ac7-59fdb3ca7dd0, initial_url.addr; http[1–4], http[6], http[8], http[21], http[36].]

On November 14, a different Woodlands-themed URL produced the title “Sign in to your Microsoft account,” but loaded its operative script, multiple branding assets, and `/web6/info` and `/web6/validatecaptcha` endpoints from a gpublicida.ru subdomain. The requests include Microsoft, GoDaddy, and Okta-named resources, plus a Socket.IO connection that received a 101 upgrade. This combination supports a configurable phishing interface with a live communication channel. It does not reveal the WebSocket messages, prove interactive operator control, or demonstrate credential submission. The image and stylesheet names alone would be weak evidence; the unrelated hosting origin, targeted entry URL, login title, and supporting endpoints together are much stronger. [scan 1d3f5cfa-5e78-420c-91ac-2d6fc075713d, scans.title; http[1–2], http[15–16], http[19], http[24], http[27], http[29].]

An additional November 14 path links a campaign-tracking URL, a Woodlands-themed destination, a Bing redirect, a WordPress-looking site, and finally an xmoslc6rdt.ru page with an email address in the final fragment. Several early records lack methods and statuses, so the exact redirect mechanism at each hop is unresolved. The later POST to the WordPress origin has a 302 response, and the Russian-domain page returns 200; a subsequent POST there has no recorded status or supplied body. These observations support layered routing and personalization, not a completed credential theft. [scan c5da55a3-0605-4b48-b409-f80af086e0ca, http[1–5], http[38], http[40], http[43]; final_url.addr.]

The plausible motives are to carry recipient context through redirects, imitate a familiar login, and gate access with challenges. However, a compromised intermediary, an intentionally operated redirector, and a copied phishing kit can produce similar artifacts. The archive does not establish which domains were compromised, identify the operators, or connect every Woodlands-named domain to one campaign. Nor does loading legitimate Microsoft or Cloudflare assets implicate those service providers. These scans document delivery infrastructure and browser behavior, not human victims entering secrets or accounts subsequently being taken over.

## September 2026: payment workflow and boundary probes

The Quidax sequence starts with ordinary-looking ramp URLs on September 19, specifying USDT/NGN conversion parameters, a public key, and unique references. The page performs initiation, transaction lookup, and refresh requests. For the sell flow, initiation and lookup return 200; the buy flow also records 200 responses. Later URLs and requests reuse the resulting transaction identifiers. This is consistent with initiating payment workflow objects, but the absent JSON bodies mean their exact state and economic effect cannot be established. There is no demonstrated deposit, settlement, or movement of funds. [scan 960b3314-f644-4832-a57e-fab108a95678, http[46], http[45], http[33]; scan 52d9be69-e168-4c93-b9f7-2f4ab04427a5, http[44], http[31], http[6].]

Resubmission of the sell initiation payload subsequently returns 400. A duplicate-reference rule is a plausible explanation because the reference and body recur, but it is not proven without the response body. A later canary-address buy attempt also returns 400. An image-tag injection placed in a status-message URL ends on a Cloudflare “Attention Required” page; no execution of that injected image is demonstrated. These probes make a security-testing interpretation plausible, while leaving authorization and motive unknown. [scan 56d37b93-a246-48d2-ac60-ebcc9d887650, http[4].request.post_data, http[4].response; scan a0622898-50c0-4b20-8803-7090b8e86c6d, http[47]; scan 8d4f4f02-66e3-465c-a181-c4cc20fbdbc9, initial_url.addr, title.]

After midnight on September 20, encoded httpbin pages explicitly probe transaction reads, OTP send/verify, a KYC `qa_reset` path, wallet-address addition, address assignment, and cancellation. One variant tries JSON requests with a public-key header; its recorded endpoint traffic consists of OPTIONS requests returning 403. This demonstrates preflight rejection in that scan, not execution of the proposed state-changing POSTs. [scan fa7c2f4c-4799-412c-9f85-0d9f38eb194b, decoded submit.url.addr; http[0–2], http[4–6], http[8].]

Follow-up variants use `text/plain`, `no-cors`, and paths without trailing slashes. These changes can avoid a JSON/custom-header preflight and avoid redirect complications; they do not bypass application authorization. The direct variant actually sends POSTs for OTP, KYC reset, wallet addition, and address assignment, all receiving 403. Some responses carry Cloudflare challenge headers; others are JSON responses with application-style headers. Consequently, “Cloudflare blocked everything” is too broad, while “the application authorized the operation” is unsupported. Another wallet-add attempt receives 404. [scan 595ea88a-07a4-445b-8a5e-288c5f9b8453, http[0–4].request.raw and response.raw; scan 328fc5f4-0ef9-441d-bb3c-e11dcb1167fa, http[4].]

The page title `e898-direct-done` is especially easy to overread. Its script catches request failures and sets that title after attempting the sequence. It means the local control flow reached its end, not that the remote operations succeeded. A cross-origin `no-cors` response is opaque to the script, so a resolved fetch need not reveal the server's actual status or body. Similarly, permissive CORS headers on some responses are not evidence of authorization bypass: the relevant responses still reject the requests. The most defensible outcome is an observable progression from workflow exploration to explicit boundary testing, with no demonstrated OTP bypass, KYC reset, wallet replacement, cancellation, or transfer. [scan 595ea88a-07a4-445b-8a5e-288c5f9b8453, decoded submit.url.addr; title; http[1–4].response.raw.]

## Competing explanations and overall assessment

The 2026 bulk activity is best explained as iterative remote data access, with the scanner used as a browser, computation environment, and observable output surface. Targeted statistical filters, historical ride-time queries, dashboard worksheet names, short diagnostic labels, and successive changes in transport support that interpretation. A conventional automated crawler could explain repeated visits, but not adequately explain programs that pack IDs into pixels, serialize results into navigation URLs, or submit forms to the scanner's own account endpoints. Conversely, those mechanisms alone do not establish malicious intent: legitimate research conducted through an awkward browser interface can produce the same workarounds.

Repetition is especially important when interpreting scale. The 1,644 whssgr.com scans cover only 81 distinct initial URL strings; 13,268 UNCTAD scans cover 6,574. These are exact-string comparisons, without normalizing query parameters or deduplicating the evidence. They support repeated experimentation or repeated acquisition, rather than thousands of independently affected organizations. They do not reveal whether retries were manual, automated, generated by an assistant, or submitted by several people pursuing similar tasks. [scans.jsonl: initial_url.domain, initial_url.addr.]

The phishing interpretation of the November material is stronger than a generic “unusual redirect” diagnosis because identity-themed interfaces and recipient personalization appear on unrelated origins together. By comparison, an ordinary scan in this same collection follows a tracking API's 303 redirect to an events page. That is a useful negative control: tracking URLs, redirects, Base64, and third-party assets are not individually sufficient indicators of phishing. Context and the role of each request matter. [scan b0921af8-4f6a-4557-b9d8-604ee8b6e87c, http[0].response.raw; final_url, title.]

The Quidax payloads are more explicitly security-oriented than the statistical retrieval programs: invalid OTP values, a QA-reset endpoint, canary addresses, and cancellation attempts are designed to test boundaries. Authorized testing and unauthorized probing remain observationally compatible. There is no supplied authorization record, operator testimony, or reliable identity evidence to choose between them. The archive also does not show that the account-workflow cluster supplied the credentials used in other episodes. Similar wrappers are cheap to copy and widely applicable; matching them is weaker linkage than matching a distinctive transaction identifier within a short sequence.

Confidence is therefore highest in mechanisms and local outcomes: browser-generated POSTs occurred; filter metadata appeared in an outgoing request; export permissions rejected certain Tableau methods; scanner authentication responses issued cookies while key creation hit a verification gate; payment probes met preflight or endpoint failures. Confidence is lower in motives, operator continuity, and downstream effects. Destination IPs identify contacted infrastructure, not submitters; submission tags and names are claims in metadata, not authenticated attribution. The supplied records provide no basis for naming a person, organization, or single campaign behind the collection. [README.txt; cited episode records above.]

The consequential boundary exposed by the archive is that scanning a URL can itself cause secondary actions. The scanner recorded activity generated by both remote pages and programs packaged into submitted URLs. Some requests were ordinary retrieval, some attempted account or payment operations, and some carried results outward. Assessing this evidence requires preserving those distinctions: successful transport is not successful exploitation, blocked extraction is not an empty dataset, and a recorded program is not proof of its execution.
